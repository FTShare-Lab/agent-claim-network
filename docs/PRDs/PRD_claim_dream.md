# Claim Dream

状态：**逐组执行、逐项候选处理及提示词精简已实现；回归与真实实验已完成（2026-09-24）。候选覆盖、名称与正文一致性、证据充分性和语义保留仍需持续评估**。

## 1. 目标与边界

Finalize / Recap 从会话中提炼 Claim；Dream 整理已经生成的 Claim。目标是提高可复用知识的质量，不以修改数量、废弃数量或提高置信度为目标。

Dream 一次完成三个任务，可以交替进行：

| 任务 | 判断与动作 | 约束 |
| --- | --- | --- |
| A 质量清理 | 将有价值的内容改写为范围明确的判断；无可挽救判断的工作流水、临时状态可 deprecated | 不能仅因置信度低而废弃有价值的假设 |
| B 证据校准 | 仅从原置信度 medium / low 的 Claim 中按需选择疑点，探索 Trace、代码和结果文件 | 有明确适用证据且能确定修订方向才修改；不确定则全部字段保持原样，不要求逐条查证 |
| C 主题整合 | 将多条内容实质整合成一条或几条，保留条件、例外和来源 | 优先复用已有 ID，承接有效信息后才废弃原项，不能只选一条原文留下 |

只修改 `holder == 当前 agent_id` 且非 deprecated 的 Claim。初始输入排除 deprecated；允许按已知 ID 读取自己的历史条目，但不能重新激活。首期不新增 Claim ID，不修改其他 Agent 的 Claim，不处理 dispute，不修改 Policy、USER.md、MEMORY.md。发生实质矛盾时只做有证据的自我修订，仲裁仍由 Maintainer 负责。

B 的固定门槛是修改前 `confidence < high`，不新增用户配置。high 免于 B 的主动查证与修订，仍进入完整上下文并可参与 A / C；免查不代表已验证为真。medium / low 也不要求逐条查证。没有可处理候选时，B 可以无操作结束。不能先降低 high 的置信度或借 A / C 组名绕过 B 的范围。

B 仅确认原判断、补证据或调整置信度时，默认只提交 confidence / evidence_summary 的必要变化，name、statement、scope、status 和 source_claim_ids 保持原样。若新证据明确证明原判断错误、不完整或范围不准确，可针对受影响部分修订，但须说明片段、依据与必要性，保留其余有效前提、动作、例外及恢复路径。不得为润色或缩短正确正文而删除知识，也不得声称“仅补证据”却提交正文改写。该约束落实于 prompt 与执行前自复核，复用字段级 changes，不新增后端语义分类或校验凭证。

查不到证据、证据不完整或冲突、模型仍不确定时，保留原 Claim 全部字段，不因本次没有结果而降置信度、标 stale / deprecated、改写正文或刷新依据。Dream 只对已有 Claim 做质量提升，不建立问题裁决状态或待办清单；跳过的 high 也不记为已验证。自述完成不等于成功，无反馈是未知，任务失败不推翻全部 Claim。

## 2. 触发与配置

只公开两个配置：

```toml
[agent.dream]
enable = true
min_interval_hours = 24
```

- `enable` 是自动和手动入口的总开关，默认打开。
- `min_interval_hours` 是自动执行距上次**成功 Dream**的最小小时数，默认 24，必须大于 0。
- 主会话启动、新建或恢复时检查；supervisor 此后固定每 **4 小时**检查。检查本身不调用模型。
- 自动门槛同时满足：距离上次成功达到配置间隔；至少 **5 条不同自有 Claim** 相对上次 Dream 输入快照发生变化。
- 变化基于完整 DTO 版本比较，包含 created_at / updated_at，同秒修改也能发现。同一 ID 改多次只算一条，Dream 自己提交的版本不再计入下一次变化。
- 首次没有成功记录时不等待 24 小时，仍要求至少 5 条。至少有一条可整理的非 deprecated Claim 才运行。
- `/dream` 绕过时间和数量门槛，保留总开关、所有权、预算和并发约束。
- 检查频率、数量门槛、输入 token 预算均为内部规则，不增加公开配置。探索轮数、总时长及输出预算暂不另设 Dream 专用限制，后续依据实验确定。

成功但没有修改也推进冷却；门槛跳过、失败和主动让出不推进。记录输入快照及本次实际写入的版本，运行期间外部产生的新版本仍保留为后续变化。

## 3. Supervisor 生命周期与队列

复用当前 Agent 的 supervisor。Dream 是 Agent 级 job，没有伪 session ID；队列优先级为 **Finalize > Recap > Dream**。

- 同一 Agent 只有一个 queued / running Dream；连续手动和自动触发复用同一 job，手动请求可升级尚未执行的自动 job。
- 启用 Dream 时 supervisor 常驻，前台退出后仍定时检查；不注册开机服务。显式 `acn supervisor stop`、进程退出或关机后，下一次 ACN 启动才恢复。
- 显式停止会中断 Dream 的模型等待和后续工具派发；已进入 Prepared 的组完成本地持久化后退出。草稿、证据和完整请求边界保存，任务重新排队，不消耗 attempt、不推进整轮成功时间；已有执行回执保持有效，远端上传继续使用持久队列恢复。
- 已开始的同一 Dream 恢复时不重查自动触发门槛，避免自身修改使变化条目数减少后提前结束；总开关仍有效。
- 关闭 Dream 后恢复原有空闲退出行为；已持久化的提交仍可恢复完成，避免半提交悬空。
- 模型探索在下一请求边界检查高优先级工作。Prepared 前让出并重新排队，不消耗失败次数；正在执行的一次 provider / 工具调用受执行预算约束。
- 使用现有最多五次 attempt。相同输入耗尽后自动检查不另开一组重试，等待 Claim 变化或手动触发。
- 每组 Prepared 后优先重放该组 checkpoint，不重复该组模型判断；恢复后仍可继续本轮其他候选。即使提交恢复耗尽 attempt，启动恢复或下一次检查仍可继续重放持久计划。
- `acn supervisor jobs` 展示 Dream；失败任务可按 job ID retry。

调度入口在 `src/supervisor/dream.rs`，队列、优先级和生命周期在 `src/supervisor.rs`。

## 4. 输入上下文、Prompt 与探索

### 4.1 初始输入

| 字段 | 内容 |
| --- | --- |
| `dream_context` | 当前 Agent、输入快照时间、工作区、上次成功时间、手动/自动来源 |
| `claims` | 尽可能全部自有非 deprecated Claim 的完整 DTO |
| `coverage` | 总数、装入数、遗漏数、排序和预算，不能将遗漏理解为不存在 |
| `policy_context` | 明确可用性和完整性；当前无独立 active Policy 缓存，标记 unavailable，不编造 Policy 正文 |
| `evidence_access` | 可用工具、工作区和运行预算 |

Policy 经 Inbox 内化为 Claim 后已经进入知识体系；Dream 不消费 pending Inbox，不扫描 Maintainer 的 Policy 存储，也不再次应用属性更新建议。需要来源信息时沿本地 Claim / Trace 查阅。

初始 Claim 预算最多 64000 tokens，并受模型窗口剩余预算限制。按 `updated_at.unwrap_or(created_at)` 从新到旧装入，容量不足时舍弃较旧项；单条超出整个预算时跳过，可通过 `read_claim` 分页探索。初始 Claim 筛选使用保守估计并预留系统提示、工具和最终输出空间；每次模型请求复用前台的请求估算器再次检查窗口，避免重复计算 canonical / replay 或将内部 JSON 转义当作额外上下文。暂不设 Dream 专用轮数、attempt 总时长或 8192 输出上限；输出沿用已选模型配置。保留每次 provider / 工具调用的既有超时、上下文窗口校验和高优先级任务让路。

探索不再按固定请求次数或时间关闭工具。模型在 B 的置信度范围内按具体疑点查证，A / C 仍可整理全部输入，按组及时暂存判断并读取校验反馈；某项已具备依据时结束该项查证，不要求穷尽所有文件。B 有具体疑点和合理查证入口时主动探索，不要求初始输入已有直接证据或确切文件路径；明确证据是修改门槛，不是开始探索的门槛。明显依赖不可获取的历史/外部材料时可以跳过，不设置最低探索或修改数量。ABC 均需说明实际处理范围；证据不足就保持原样，不能把未知当作事实反证或废弃理由。

Prompt 要求同一模型结束前认真检查整轮工作：A 使用一致标准检查全部已装入正文；B 对已识别疑点判断下一步观察是否有价值，必要时沿适用线索核对直接相关的实现、契约或结果，而不把读过目录/概述当作具体查证完成；C 可以保留分开的知识。一组已执行不代表整轮完成。有价值且可行的候选应继续处理，判断无必要、材料不可得或仍不确定时可以保留，并在总结简述实际覆盖、代表性停止理由和未覆盖范围。整轮覆盖仍由提示词引导；后端仅约束已登记候选逐项处理，不固定 ABC 顺序，不增加独立复核、后端覆盖率门槛或最低调用/修改量；宁可保留不确定内容，也不产生无依据修改。

完整请求边界的上下文、文件回执、已完整读取的 Claim 和已接受的分组草案保存于 `runtime/supervisor/dream_exploration/<job_id>.yaml`。同一 job 重试时核对输入版本、工作区、prompt、模型身份、输出配置与所有已读文件版本；匹配才复用，不匹配就重新审查。分组提交在同一次工具循环内返回组/Claim/字段错误，允许局部修复；失败提交保留此前已接受的组。无进展的 provider 重试不累积同一错误反馈或失败的自由文本计划。探索记录不是 Prepared，不授予 Claim 写权限，也不推进成功时间；只有第 5 节的校验与 Prepared 提交流程可以写 Claim。

### 4.2 上下文压缩与历史查询（已实现）

- 每个完整工具交互结束、下一次模型请求之前，输入估算超过 160000 token 自动压缩。实际阈值取 `min(160000, context_window - max_tokens - 4000)`，小窗口或较大输出预留会提前触发，不新增公开配置。
- 先将完整请求历史不可覆盖地保存到 `<agent_home>/dream/<job_id>/history/<input_fingerprint>/`，再生成四字段探索摘要：已检查范围、发现、不确定性、下一步。摘要调用不带工具，单次输出内部限制为最多 4096 token；这不是 Dream 探索轮数或输出上限。
- 后端重建初始 Claim 快照、额外完整读取的 Claim、实际接受草稿、待修复错误、校验/复核版本和证据索引；这些状态不能交给摘要模型改写。保留预算内最近四个完整消息段以及当前 runtime context，工具调用和结果不得拆散。
- 压缩目标不超过触发阈值的 75%。摘要输入中的长消息只提供明确标记的预览，完整历史仍在归档；摘要不构成证据或事实确认。原始证据收据继续保存在探索 checkpoint，提交时仍检查版本。
- `dream_read_history` 只查询当前 job、当前输入版本的历史。省略 archive_id 列出快照；指定 archive_id 后可按 keyword/tool_call_id 搜索，用 message_index、char_offset/max_chars 分页读取原文。它不能访问任意路径，不生成新的 evidence receipt，不替代 dream_read_draft 或重新读取变化后的文件。
- 摘要、归档或新窗口容量验证失败时，不替换旧上下文、不丢草稿、不提交 Claim；沿用 supervisor 重试。结构化状态自身已无法容纳时明确失败，不截断关键状态。
- 新窗口与探索摘要随 checkpoint 持久化，重试仍需核对原有 Claim 和文件版本。重复压缩保留以前的快照，清除旧 provider continuation 链，继续使用新上下文。

### 4.3 Prompt

实际模板为 [claim_dream.j2](../../prompts/claim_dream.j2)。Dream 通过模板 include 完整复用 [what_is_claim.j2](../../prompts/what_is_claim.j2)，不使用删节版或另写一套 Claim 定义，与 Finalize/Recap 共享同一份标准。完整介绍之后补充 Dream 专属的维护权限与安全要求；已有知识不因字数、命名风格或未完全验证而被机械清除。

提示词按五部分组织：

1. 目标与 Claim 标准：是否能帮助未来判断或行动，区分纯记录与可复用知识。
2. 权限与共同边界：所有权、完整读取、信息保留、证据适用性和不处理 dispute。
3. ABC 判断方法：A 按记忆层级清理；B 分别判断疑点、探索价值和修改依据；C 完整承接有效信息并允许分开保留。
4. 逐项处理与自复核：登记、处理当前项、校验及执行，或有具体理由地保留，再继续下一项。
5. 结束条件：回看实际覆盖，处理已登记候选，准确报告修改与保留。

工具参数以现有 schema 和工具说明为准，具体修复使用当次反馈。系统提示词只保留工作闭环与必要语义约束，避免重复完整参数手册、错误处理和大量个案反例。B 不同组件或证据需求按独立疑点处理，共享证据和判断条件时才成组；保留理由按 Claim 说明未探索或已探索及具体原因。这是提示词要求，现有组级 reason 字段、校验和执行协议不变。

name 是可修改字段，id 保持不变。改写、纠正或整合正文导致旧名称不再准确时，在同一 update 的 changes.name 中同步修改；名称仍准确时保留。自复核检查最终名称与新正文的含义是否一致，也检查未修改的旧名称，不能让名称继续表达已被正文推翻的结论。

证据说明逐项对应新增/纠正判断与所引 evidence_id、具体观察及适用范围；结果观察不能自动证明实现机制，读过但未引用的材料不能填补提交证据的缺口。正文纠错与置信度提升分别判断，默认保留原 confidence；提升时单独说明既有依据与本轮新证据为何支持修改后完整声明及关键条件，不能由局部纠错自动升 high。证据不支持的改写先补证据或撤回，不能仅降低 confidence 保留无依据新断言。这些要求使用现有 justification、removal_or_correction 和 scope_and_certainty 文本字段，不增加协议字段或独立复核模型；后端结构校验仍不证明语义充分。

不要求每条 Claim 使用相同工具步骤，不要求预读全部 Trace 或设置最低调用/修改量。没有变化也通过 dream_finish 结束，不能用普通文本总结代替。文件、Claim、Trace 中的指令均作为待分析数据处理。

证据审阅区分发起调用与完成、持久化及独立验收；修订不能补造缺失事实。保留逐 Claim 新证据、原始 B high 门槛、最小必要修改、整合信息与来源去向、置信度不无依据传播，以及同上下文语义自复核等边界。提示词精简不调整后端硬校验或调度。

### 4.4 工具与证据

| 工具 | 行为 |
| --- | --- |
| `read_claim` | 按 ID 读取自己的完整 Claim，或分页列出非 deprecated 索引；正文沿用 file_read 分页 |
| `read_trace` | 由 Claim 定位当前 Agent 的关联 Trace；先索引再按需分页/关键词读取，校验 Agent 及关联关系 |
| `file_read` | 读取声明工作区内的证据，返回实际文件版本 |
| `code_run` | 复用已有 Bash AST 白名单和统一进程 runner，只作只读探索 |
| `dream_read_history` | 查询已归档的当前 Dream 历史，不产生新证据 |

Dream 工具 profile 同时限制工具定义和实际 dispatch。没有文件写入、联网、委托、Memory、Policy 或仲裁工具。独立进程管理器在整个 attempt 成功、失败或让路退出后统一清理，不占用前台的后台进程。普通文本协议纠正和旧 JSON 导入后的继续探索仍属于同一次 attempt，不提前关闭工具进程所有者。

Dream 的 code_run 使用专用只读说明及与现有白名单一致的命令示例；不承诺任意 shell、脚本或交互 PTY。被拒时返回可用语法提示。自复核阶段仍可调用探索工具；dream_finish 成功后停止模型采样，进入 Prepared 提交。

初始 evidence_access 包含受限 PATH 中的命令可用性，工具在执行前检查白名单命令是否存在，避免缺失命令被管道末端的成功掩盖。不扩展宿主 PATH 或沙箱权限；不可用时提示 ls/grep、file_read、read_trace 等已有替代入口。工具失败不视为 Claim 缺少证据。

草稿 schema 按 keep/update/deprecate 区分允许字段；deprecate 仅可改 evidence_summary，由宿主设置状态。operation_feedback 一次列出所有违规字段，失败不改变已接受草稿。整合回既有来源 Claim 本身时，不要求在该输出上添加自引用；原始来源边与 coverage 随执行计划持久化。其余来源必须仍保留在相应存活输出，循环与新造来源仍禁止。C 无最低整合数量；保留独立知识可以是最终结果，整合必须同时保留正文及依据中的条件和证据边界。


只读命令同时校验 cwd、参数路径和符号链接，并清除继承环境。macOS 使用系统 sandbox-exec；Linux 使用 bubblewrap 的只读工作区与系统运行目录，隔离网络并遮蔽私有路径。缺少隔离器或运行环境不支持时，命令明确失败，模型仍可使用 file_read；不回退到无隔离执行。原白名单不扩展为任意测试或构建能力。

宿主保存每次实际工具调用的证据回执。每项 B 修改（包括正文、scope、置信度、状态、废弃或仅更新依据）都必须输出新的 evidence_summary，并在该 Claim 的 change_basis.evidence_ids 中引用本轮 file_read 读到的、带版本的直接文件证据。证据摘要说明具体观察及其与修改的支持关系；只在组级引用其他条目的证据不够。新证据指本轮实际取得、支持本次修改的观察，不要求证据文件刚被创建或修改。仅确认原判断且没有字段变化时可保持原样，无需刷新依据或更新时间。read_claim / read_trace（尤其历史 Dream 报告）只作知识或来源记录，不能单独证明任务成功。命令结果用于定位，作为修改依据时必须有关键文件的版本回执。文件版本在提交时复核，失效则跳过关联组。

这些检查保证权限和证据出处；提交前在同一 Dream 上下文进行双向自复核。证据是否充分仍依赖模型判断，复核通过不代表自动证明 Claim 为真。

## 5. 逐组校验、语义复核与执行

### 5.1 当前工具流程

模型发现可修改项或具体查证疑点后，立即以 `dream_record_candidates` 登记，沿用 `group_id`，不新增条目 ID。按模型选定的顺序处理第一项：探索后形成方案，或基于具体安全/无须修改的理由保留。已有完整方案时，可直接 `dream_stage_group` 自动登记并暂存完整操作组。当前项执行或明确保留后才处理下一项。`dream_stage_group` 暂存完整操作组，`dream_validate` 返回真实 before/after、差异、证据和 validation_id。模型在原上下文语义复核后调用 `dream_apply_group` 执行，再继续其他候选。`dream_finish` 只汇总并结束本轮，不负责统一执行。ABC 均允许保持原样，不以修改数量为目标。

```text
dream_record_candidates { candidates: [{ group_id, claim_ids, kind, reason }] }
dream_keep_candidate { group_id, reason_kind, reason }
dream_stage_group { group_id, group: {
  kind, reason, evidence_ids, coverage,
  change_basis: [{ claim_id, removed_or_changed, added, justification, evidence_ids }],
  operations: [{ id, action: keep | update | deprecate, changes?: {...} }]
} | null }
dream_validate { group_ids?: string[] }
dream_apply_group { group_id, validation_id, review: {
  claims: [{ claim_id, information_preserved, removal_or_correction,
             factual_correction, output_ids, evidence_ids }],
  scope_and_certainty
} }
dream_read_draft { group_ids?: string[] }
dream_finish { group_ids: [], review: { quality, evidence, consolidation } }
```

- A/B 的独立 Claim 建议单独成组。C 的整合结果和来源 deprecated 必须在同一组，不能先废弃再补结果。
- 登记不改变 Claim，也不要求给所有未变 Claim 建候选。批次登记全部校验后接纳：必须已完整读取、自有、非 deprecated；B 仍限原始 medium/low。同一 Claim 不进入多个待处理组。
- `reason_kind` 仅接受 insufficient_evidence、useful_knowledge、uncertain_preservation、no_consolidation_benefit、external_change，并要求具体说明。其他任务、优先级、已有其他成果不是保留理由。后端检查类别与结构，不能证明自由文本理由成立。
- 当前登记项的目标 ID 和任务种类必须与暂存、校验及执行一致；可显式扩充/调整登记，但不能静默丢掉原目标。新登记不使旧的部分校验可用于执行。
- 暂存组可就地替换或撤销，失败不覆盖已接受草稿。`group:null` 只移除草稿/错误，候选仍需执行或通过 keep 工具明确保留；已执行组离开草稿，不会被撤销。
- 校验、探索、复核不直接写 Claim；apply 是唯一的新模型执行入口。返回实际变化 ID 和最新 Claim，后续判断以新版本为准。
- 每个输入 Claim 都要说明保留的有效规则/条件/例外、删除或纠正原因、信息去向；C 的 keep 输入也不省略。name/body、scope、确定性与来源边界在组级说明。
- 不再要求模型重复抄写四个字段并覆盖全文，也不引入复核条目 ID。失去逐字覆盖的机械防漏能力是明确取舍，保留逐 Claim 依据与整合去向，语义质量需要实验评估。
- B 修改及混合在 A/C 中的事实纠正必须有该 Claim 的新 evidence_summary 和版本化直接 file_read 证据；high 门槛同时检查本轮原始状态，不能通过先前操作降级绕过。
- 置信度提升必须有该输出自己的新证据；C 不得无依据继承较强置信度或丢失来源引用。所有权、不可变字段、来源环、完整读取及证据版本检查继续复用原校验。
- 新证据只支持具体适用对象和条件；旧 Claim、Trace、本轮执行回执不能自证。后端不能证明语义正确，模型不确定时应通过 keep 工具说明具体理由并保持原 Claim。
- 旧完整 JSON 计划可导入草稿，但必须继续 validate/apply；已经 Prepared 的旧任务保留原提交恢复兼容。

### 5.2 执行记录与恢复

执行工具强制在 `<agent_home>/dream/<job_id>/executions/` 保存完整执行计划，再写 Claim。每次执行有 YAML 恢复检查点、JSON 完整记录和 Markdown 人工视图，包含 before/after、证据、简要语义复核、硬校验结果、时间、实际写入与冲突状态。记录失败时不能开始写 Claim；写入后失败则从已经持久化的记录恢复，不宣称没有修改。

复用原有 Prepared 提交代码、单文件原子写和知识应用锁；模型请求期间不持锁。不宣称多文件具备数据库事务原子性。组内先写存续结果，再废弃来源。恢复时允许当前等于原版本或目标版本；遇到第三方版本或证据变化，停止本组剩余修改，已经写入的结果仍有审计记录和同步暂存。

`runtime/supervisor/dream_pending.yaml` 标识正在恢复的组。read_claim 和会话 runtime_context 不暴露这段未完成状态；supervisor 在执行下个任务、自动/手动检查或重试前恢复持久化提交。同一 validation_id 重复执行只返回已有回执，不生成新时间戳、Trace 或上传任务。

- 整轮后续失败不撤销已生效组，沿用 supervisor retry，并在错误信息中明确部分成果可能已生效。
- Dream 自己写入的版本不使探索恢复指纹失效，也不计作新的自动触发变化；外部变化仍会使相关旧校验失效。
- 仅整轮 finish 后更新 last_success_at；每组执行不启动新冷却窗口。整轮起点版本加本轮实际写入版本形成基准，不把运行期间未处理的外部变化吞掉。
- 已执行 Claim 可在后续组继续处理，但必须依据最新原文重新校验。不能把本轮结果作为新的独立证据或绕过原始 high 门槛。
- 每组持久化后复用已有团队 staging/upload；单人模式仍不请求团队服务、不创建待补传队列。本地成功和远端上传成功分开描述。

### 5.3 审计和上下文

`origin.yaml` 保存本轮起点，`input.json` / `inputs/` 保存输入，`revisions/` 保存草稿和反馈，`executions/` 是逐组实际执行依据，`history/` 保存压缩前历史。`dream_read_draft` 同时展示未执行草稿和已经生效的操作及最新 Claim。压缩和恢复保留准确执行状态，模型摘要不能覆盖它。

`dream_finish` 要求已登记候选全部执行或明确保留，同时没有未执行组及待处理错误，只提交 ABC 实际范围说明。完成其他组不能绕过该检查。候选进度保存在草稿、每步反馈、审计和准确压缩/恢复输入中；旧检查点缺少此字段时从已有草稿组补齐。后端不能观察模型尚未登记的想法，所以不宣称全面覆盖所有 Claim。`result.json` 和 `report.md` 汇总执行结果；失败或未结束时仍可直接查 executions。记录的是可核查理由，不要求模型内部思考。没有 Claim 裁决状态或仲裁待办。

实现分工：`dream_execution.rs` 编排逐组执行与回执；`dream.rs` 复用 Prepared 写入和调度状态；`dream_draft.rs` 暂存/校验/执行工具；`dream_candidates.rs` 本轮候选顺序及处理结果；`dream_plan.rs` 权限、证据与整合约束；`dream_audit.rs` 人工视图；`dream_exploration.rs` 与 `dream_compaction.rs` 保存和恢复上下文。`dream_review.rs` 的旧全文引用协议仅保留历史兼容路径。

## 6. 通用的会话 Claim 变化通知

此能力面向 **所有 Claim 变化来源**，独立于 Dream 开关。

- 每个 session 保存与其 system prompt 使用的同一份 Claim 快照索引，原 system prompt 保持固定。
- 每个主 turn 观察本地库，生成相对初始快照的累计差异；具体项只有 ID、name、scope，以 change 标明 created / updated / deprecated / removed。
- 放入已有 `<runtime_context>`，沿用 Asia/Shanghai（UTC+8）时间及工作区信息。需要正文时模型调用 `read_claim`。
- 最新差异快照覆盖旧通知；既有 ModelContext fingerprint 去重，相同内容不会反复注入。先新增后删除的条目保留 removed 提示。
- 不设置 Agent 级共享消费游标。多个会话各有基准，各自收到变化；Resume 继续使用该会话的 baseline 与已持久化 ModelContext。
- 复用 Provider WAL、失败恢复和 compaction 投影，没有“通知未送出、已读游标却提前推进”的窗口。
- 获取知识锁时不等待长任务；锁忙则保留先前通知，下个 turn 重试。read_claim / read_trace 也拒绝读取正在提交中的半完成快照。
- 旧 session 没有 baseline 时发送 refresh_all 提示，不能静默将当前库当作已读。

实现位于 `claim_context.rs`、主会话 context appender 和 provider-neutral turn loop。通知是运行状态，不代表 Claim 已获得验证。

## 7. TUI

- `/dream` 出现在 slash 补全和 help 中，前台模型忙时仍可入队，不消耗前台任务槽。
- 手动请求显示 job ID、入队或已有任务信息，并观察运行、重试和最终状态。仅在状态、attempt 次数或失败原因改变时追加通知；自动重试中保留上次原因，成功后清除。

- 自动门槛不满足时不刷屏；TUI 退出后通过 supervisor jobs 查结果。

### 零操作结束的一次反馈（已实现）

输入非空、尚无候选登记、探索回执、修改提案及已执行组时，第一次 `dream_finish` 返回一次 ABC 边界提示与真实活动统计。模型可以继续探索或提交草稿，也可以说明代表候选的保留依据后再次结束。提示状态随草稿保存，恢复同一草稿后不重复；没有最低工具调用或修改数量，不增加独立复核模型，不调整成功冷却和自动触发门槛。A/C 可处理 high，B 的 medium/low 门槛不能泛化为整个 Dream 的操作限制。
